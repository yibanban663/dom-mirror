# 短时断线恢复验收（2026-10-26）

目标版本 0.10.0。使用现有 Vikunja v2.7.1 固定镜像、隔离 internal Docker 网络、临时 SQLite 与合成账号；不接入真实用户数据。应用镜像为 `vikunja/vikunja@sha256:f7dc8428d10aef17f3075886d3c1c022f566ec456f88985f02c137f4fc534576`。

## 复现

```bash
docker build -t dom-mirror:local .
IMAGE=dom-mirror:local SESSION_GRACE_MS=2000 \
  BUSINESS_TEST_SCRIPT=verify-recovery.cjs EVIDENCE_DIR=artifacts/recovery \
  bash tools/verify-docker-vikunja.sh
```

服务端与浏览器分别运行在有资源限额和 timeout 的容器中，无宿主监听端口；脚本退出清理容器和网络。测试使用 2 秒保留期加速过期分支，生产默认值仍为 60 秒。视口 1280×900，DPR 1。账号、密码、业务 API token 和恢复凭据不进入结果文件；API 只用于预置账号/项目及独立读取持久状态。

## 验收口径与结果

以下四项在 DOM、frame 各验证一次，两种通道均通过：

| 场景 | 操作及独立断言 |
|---|---|
| 登录、路由与草稿 | UI 登录并进入项目，输入未提交草稿；命令队列 ping 屏障后关闭 WS，自动恢复后凭据保持同一会话、草稿完整，仍在原登录项目 |
| 提交已落库、UI 确认丢失 | 测试专用 WS 监听阻止客户端接收显示更新，UI 只按一次 Enter；API 确认已创建而客户端没有任务行，随后关闭 WS；恢复后任务可见、输入框清空，API 同标题记录数为 1 |
| 同账号会话隔离 | 第二独立浏览器上下文初始仍需登录，使用同账号登录后，两页面分别保留不同草稿；恢复第一页面不改变第二页面，release 第一会话后第二页面仍能提交并被 API 确认 |
| 过期和显式重新开始 | 主动断开 WS，并在测试端阻止后续握手超过保留期；再次连接收到终止错误，页面 inert，原凭据不变；用户点击“重新开始”后才创建新会话并回到登录页 |

服务端日志同时观察到 release/过期后的 Chromium 关闭及会话计数回到 0。会话单元测试另覆盖保留期间容量占用、过期名额释放、活跃连接拒绝接管、错误来源/无效凭据拒绝、旧 socket 不能继续投递命令、关闭仅清理一次。

本地恢复证据目录：`/home/Kei/dom-mirror-validation/20261026/recovery/final-recovery/`（result.json、截图、镜像 ID、应用版本及三端日志）。CI 使用相同入口，并以 `recovery-regression` artifact 保存每次运行证据；远端结果应以对应提交的 CI 状态为准。

## 限制

此处通过主动关闭 WS 模拟短时断连，通过测试端过滤显示消息模拟确认丢失，并非物理断网、TCP 黑洞或任意时刻中断应用 HTTP 请求的完整故障矩阵。提交唯一性只证明该用例没有自动重放，不提供业务 exactly-once 事务保证。

刷新页面、服务进程重启、密码/文件值回填、离线编辑、退出登录、长稳与容量压测均不在本次验收范围。未送达源站的输入不保证保留。客户端和服务端必须同步升级。
