# 单实例并发容量与资源预算：合成看板

在固定合成看板、镜像服务 2 CPU / 2 GiB 下，DOM 的 1/3/6 会话均满足本轮预算。frame 的冷启动、交互与峰值内存预算通过，但回收后匿名内存增量不稳定或超预算；完整矩阵 12 组功能通过，7 组满足全部预算。结果只覆盖此工作负载，真实业务容量、长期运行与最大并发仍待验证。

## 观测器复核

初轮观测器把已关闭的 Puppeteer Browser 对象保存在数组内，存在延长会话闭包/缓冲区生命周期的干扰风险。观测器已改为只保存 PID、connected、closed 标量，并按原计划完整重跑上述 12 组；引擎代码和预算未变。本报告统计及结论只使用修正后的矩阵。初轮及其 60 秒空闲观察保存在旧目录作审计，不作为最终内存证据，也不将两轮数值之差直接归因于观测器。

## 修正观测器后的 60 秒空闲观察

正式修正矩阵结束后，另测 frame / 3 会话，只将驱动中回收后等待从 3000ms 改为 60000ms。使用独立镜像和目录，保持标量观测器、引擎、sharp 默认缓存及其余工作负载不变，不启用强制 GC；该组不混入正式矩阵，也不改变原来的 3 秒 / 64MiB 预算。

补充组匿名内存基线约 **32.4MiB**；全部所跟踪的 Chromium 主进程回收并空闲 60 秒后约 **147.2MiB**，仍高出 **114.8MiB**。cleanup 阶段约第 6、18、33、63 秒的增量分别约为 114.9、114.8、114.8、114.8MiB。延长空闲未消除残留，单轮实验仍不能区分活跃引用、原生缓存、allocator 保留与持续泄漏。

下一步记录 frame 生命周期中的 Node external/arrayBuffers、sharp 缓存及进程内存，并做重复建立/回收周期对照，先定位内存归属，再决定释放或复用策略。当前不提高默认会话上限，真实业务并发与长稳仍待验证。

## 冻结条件

运行前固定 [capacity-plan.json](../../tools/fixtures/capacity-plan.json) 中的矩阵与预算。每组使用全新的镜像服务和客户端容器；DOM / frame 各测 1、3、6 会话，各重复两轮。功能失败或 OOM 后停止该模式继续加压；性能预算未通过照实报告，不修改标准让结果通过。

- 镜像服务：2 CPU、2 GiB，按本组并发数设置 `maxSessions`。每会话独立服务端 Chromium。断线保留期固定为 3000ms，以便验证名额占用和过期回收；这不是生产默认值 60000ms。
- 客户端及合成源站：另一个容器，4 CPU、4 GiB，每用户一个客户端 Chromium，1280×900、DPR 1。源站、客户端驱动和客户端渲染资源均不计入镜像服务 CPU/内存；同时记录该容器资源，识别压测端瓶颈。
- 页面：150 行合成客户表、4 张指标卡、Canvas 柱状图、输入框、结果及光栅序号标记。表格使用固定高度内部滚动容器。无外部网络、真实账号、字体混淆或无限动画。
- 每用户实际鼠标聚焦并输入，然后 3 次预热、20 次正式 Enter 操作。所有会话同步发起一轮操作，每轮至少间隔 1 秒；操作未完成时不叠加下一轮。报告实际完成速率，不能把闭环减速当作仍维持 1Hz 的开放负载。
- 每次操作在客户端观测结果，在源站独立记录 `{session,index}`。检查每个源站会话都有唯一且完整的 0–22 序列；不把别人的回执算入当前用户。
- 超过上限时检查 `SESSION_LIMIT` 且未启动额外浏览器；关闭客户端后，保留会话仍应占满名额。过期后检查所跟踪的业务 Chromium 主进程消失，原 token 返回 `SESSION_EXPIRED`，新会话可入场并再次释放。

预算：最慢会话冷就绪 ≤15 秒；每用户 P95 的最大值，DOM ≤500ms、frame 绘制 ≤1000ms；镜像服务采样峰值内存 ≤1638.4MiB（2GiB 的 80%）；回收后匿名内存较基线增长 ≤64MiB；OOM kill 增量为 0。预算来自本轮预先设定的验收目标，不代表包对使用者的保证。

## 指标口径

冷就绪是客户端打开镜像页面到镜像 DOM 与 `sync-ready` 屏障完成；不包含压测端 Chromium 启动，也不是首像素或主机冷缓存启动。

DOM 延迟从客户端捕获的真实 Enter keydown，到 MutationObserver 看到对应序号文本。frame 主指标从同一 keydown 到 `xy-tiles` 画布像素回读确认对应颜色已经由 `drawImage` 绘制；另记录两次 requestAnimationFrame 后的绘制机会，但不称为实体屏幕呈现时间。不能用 DOM 结果替代 frame 像素更新。探针来自 [profile-client.cjs](../../tools/profile-client.cjs)，引擎不做时序插桩。

每个用户有 20 个正式样本，P95 使用 nearest-rank；汇总同时保存合并分位数和最慢用户的 P95。两个重复不合并来掩盖轮次差异，不能据此报告 P99。

镜像服务每 250ms 读取 cgroup v2 的 `memory.current`、`memory.stat`、`memory.events`、`cpu.stat`。内存含 Node、业务 Chromium 与文件缓存；平均 CPU 是正式操作阶段全容器使用的核数，包含每秒操作间的空闲，不是峰值 CPU。节流时长是 cgroup 累计指标，不等于每个业务请求增加的延迟。

回收检查独立确认业务 Chromium 的关闭完成及 `/proc/PID` 消失。内存比较采用基线和过期后额外等待 3 秒的 `memory.stat.anon`，不要求文件缓存立即回到基线，也不把匿名内存的短期回落当作没有内存泄漏的长期证明。

## 本地运行环境与证据

WSL2 Linux x86-64，24 logical CPU，约 94GiB 主机内存；镜像内 Node `24.21.0`、Chrome for Testing `156.0.8078.47`、Puppeteer `25.16.0`、sharp `0.35.5`、ws `8.22.0`。主机并非专用物理压测机，结果存在调度与缓存影响。压测端正式阶段平均 CPU：DOM 约 0.023–0.117 核，frame 约 0.168–1.336 核，低于其 4 CPU 配额；本地网络和 headless 呈现仍需在真实终端上另行验证。

复用缓存中版本不变的依赖运行时，在新镜像复制当前应用和测试代码并运行 `npm ls --omit=dev`，不代表本轮完成标准 Dockerfile 的全新在线依赖安装。修正矩阵全部使用同一镜像和源码/脚本摘要。

有效证据根目录为 `/home/Kei/dom-mirror-validation/20261026/capacity-corrected/`；初轮另保留在 `capacity/`，不混入最终统计。这是本地实验；容量矩阵作为手工基准，不接入每提交必跑的 CI，也没有执行远端 CI。

## 复现

在有足够剩余 CPU/内存的本地 Docker 主机执行，避免生产负载或其他压测干扰。脚本使用 internal Docker 网络、无宿主端口和临时容器，不使用已有业务。每组客户端有 150 秒上限，镜像服务 180 秒；退出时保存证据并清理本组容器和网络。

```bash
docker build -t dom-mirror:local .
IMAGE=dom-mirror:local EVIDENCE_DIR="$PWD/artifacts/capacity/run-1" \
  bash tools/run-capacity-matrix.sh
```

单组调试：

```bash
IMAGE=dom-mirror:local CAPACITY_MODE=frame CAPACITY_SESSIONS=3 \
  EVIDENCE_DIR="$PWD/artifacts/capacity/single-frame-3" \
  bash tools/verify-docker-capacity.sh
```

完整矩阵输出 `plan.json`、每组客户端操作/资源、源站回执、镜像服务资源、源码摘要、镜像 ID、容器退出状态和日志，最后生成 `summary.json`。重新汇总不运行业务：

```bash
node tools/summarize-capacity.cjs artifacts/capacity/run-1
```

功能不完整时汇总脚本返回非零；性能预算未通过时保留 `withinBudget: false`，采集过程仍可成功完成，以便看清退化档位。原始证据不保存登录凭据或恢复 token。
