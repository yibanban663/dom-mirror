# 0.10.0 续测：关联帧定位等待

沿用[客户端标记与解码复用实验](2026-10-26-codec-and-presentation.md)的基线、源站、镜像、视口和隔离环境。生产实现未改。正式实验固定 PNG 原路径、2 CPU / 2 GiB、60ms 补丁合并窗，唯一对照参数为测试进程内的帧消费间隔 16ms / 4ms。

结论：当前单会话创建任务场景的大头在“Node 开始处理 Enter → 对应源站帧到达 Node”，其次为服务端图像处理。缩短帧轮询间隔降低了排队，但增加消费帧数和 CPU，未证明端到端延迟稳定下降；保留生产 16ms 默认值，不引入 Rust/Wasm。

## 关联方法及验收

测试客户端给真实 Enter 消息添加独立操作编号；源站任务 DOM 观察器更新同编号的颜色标记。服务端在解码后的实际帧中读取标记颜色，为该帧附加编号、帧序号及分段耗时。客户端将收到的 tile URL 关联到实际 Image、load 事件与 drawImage，再检查画布像素。

只在 `profile-server.cjs` 进程内源码副本中追加 `_profile` 元数据，普通服务没有协议变更。数据仅包含数字编号与时间，不包含键入内容、密码或恢复凭据。

- Node 内测量：命令入队、开始处理、CDP 帧回调、消费开始、图像处理完成。
- 客户端内测量：真实 keydown、消息回调、Image.src 设置、load、画布像素匹配、两次 rAF。
- 源站浏览器内测量：Enter keydown 到任务 DOM 标记更新；通过独立回调返回该间隔。
- 不直接相减不同进程的绝对时间。客户端 keydown→收消息区间减去服务端入队→序列化前区间，得到的只是两端调度、传输、序列化等未覆盖部分的**合计余量**，不是单向网络延迟或 RTT。

正式 16→4→4→16 顺序，每轮 3 次预热、20 次正式创建；每轮独立合成账号、项目、浏览器、网络与数据库。92 条业务记录均由 UI 创建并独立 API 确认，80 个正式样本全部关联成功。每项关联均验证操作编号、客户端分段恒等式、服务端分段恒等式和非负服务端间隔。四轮“DOM 正常更新但拦住画布绘制”的负对照也通过。

另有一轮初始探针验证 tick16-1，20/20 关联成功；不计入下表正式 ABBA 对照。探针仍只支持单会话，不能直接拿全局操作编号映射用于并发容量报告。

## 生产默认 16ms 的分段结果

以下范围是两轮各自 P50 的范围，不是相加的预算或合并分位数。

| 环节 | P50 范围 | 测量边界 |
|---|---:|---|
| Node 命令队列等待 | 0.023–0.029ms | 命令进入队列到开始处理 |
| 开始处理 Enter → 对应帧到达 | 48.4–56.4ms | 包含 CDP 输入派发、源站业务/UI 更新、渲染/捕获/PNG 产生及帧回调 |
| 帧到达 → 消费 | 3.9–5.8ms | latest-frame 缓冲区与轮询/忙碌等待 |
| 消费 → 图像处理完成 | 11.7–11.9ms | 解码、像素扫描、裁剪编码及少量编排 |
| 客户端收到消息 → Image.src 设置 | 约 0.2ms | 消息处理与 draw chain 排队 |
| Image.src → load | 2.0–2.5ms | 包含图片解码及事件调度，不是纯解码 CPU 时间 |
| 收到消息 → 标记像素验证成功 | 6.9–7.0ms | 包含画布绘制和探针读回 |
| 未覆盖区间合计余量 | 1.4–1.5ms | 本地 Docker 网络下的两端调度、传输等合计，不能外推 WAN |

源站浏览器自身的 keydown→任务 DOM 标记更新 P50 为 22.1–23.0ms；标记回调到达 Node→匹配帧到达 Node 的 P50 为 23.0–24.9ms。这些观测支持继续细分源站 UI/渲染/捕获阶段，但不是纯 API、纯渲染或纯编码耗时，且不能与上表重叠区间直接相加。各段 P50/P95 来自不同请求排序，也不能相加来重建端到端分位数。

## 4ms 轮询对照

| 轮次 | 帧排队 P50 / P95 | 标记画布验证 P50 / P95 | 消费 / 收到帧数 | 镜像容器平均 CPU |
|---|---:|---:|---:|---:|
| 16ms / 1 | 5.82 / 13.81ms | 83.8 / 107.3ms | 196 / 266 | 0.722 核 |
| 4ms / 1 | 1.97 / 6.62ms | 83.4 / 105.3ms | 228 / 264 | 0.775 核 |
| 4ms / 2 | 1.41 / 3.76ms | 73.0 / 116.3ms | 234 / 266 | 0.775 核 |
| 16ms / 2 | 3.90 / 5.90ms | 78.1 / 107.5ms | 191 / 257 | 0.738 核 |

4ms 更频繁地消费中间帧，latest-frame 缓冲覆盖次数从 66–70 降到 32–36。消费帧数增加约 16%–23%，整个生命周期平均 CPU 增加约 5%–7%；正式样本端到端 P95 没有稳定改善，图像处理段 P95 反而为 43.4–46.5ms（16ms 两轮为 26.6–29.0ms）。容器仍出现 CPU 配额节流，不能把这些差异全归因于轮询频率，也不能据此宣称固定收益或容量。

本实验同时说明：缓存覆盖中间帧并不等于业务输入丢失。正式 80 次创建均持久化且观察到对应帧；业务命令没有被跳过，覆盖的是尚未消费的屏幕帧。

## 探针自身开销

为确认真实颜色，客户端在 drawImage 后调用 getImageData 读取一个像素。该读回 P50 约 4.0–4.1ms，约占上述客户端消息→像素验证时间的一半以上；drawImage 调用自身大多低于浏览器时钟分辨率。

读回时间可能同时包含等待已提交绘制完成与读回开销，不能直接全部减掉，不能把它误认成生产客户端固有的 JS 计算瓶颈。PNG 验证标记也不证明整条任务文本已逐像素正确显示；两次 rAF 是后续渲染机会，仍不等于物理屏幕呈现时间。当前结果是带探针的定位证据，不是无干扰 SLA。
