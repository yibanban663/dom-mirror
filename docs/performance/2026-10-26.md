# 0.10.0 性能调查：是否需要 Rust / WebAssembly

结论：暂不迁移整体服务。DOM 链路没有使用 frame 像素扫描；frame 的 Rust 扫描内核确实更快，但其占比有限，Wasm 还受数据复制影响。当前更值得继续调查的是快照/补丁调度、截图与 PNG 处理、消息体积和客户端呈现。

这是有时限的单会话定位实验，不是容量、长稳或生产 SLA 验收。生产 server.js、客户端和依赖均未修改；16ms 合并窗只作用于测试进程内的源码副本。

## 条件和口径

- 基线提交：`e8341a5d3a55ce28eddc5b11d6f2b6bd29d93fae`，版本 0.10.0。
- 镜像：`sha256:93e65743eb438e03ccdc78423a7374dd16466f19208744c410c3cf4e0550912f`，在测试容器内只读挂载当前调查脚本；profiling 时额外挂载同一基线的 server.js。
- 源站：Vikunja v2.7.1，固定镜像 digest 沿用[业务验收记录](../acceptance/vikunja-2026-10-26.md)。每轮独立 internal Docker 网络、临时 SQLite、合成账号及空项目，无宿主端口；完成后自动清理。
- 主机：WSL2 Linux 6.6，x86-64，24 logical CPU，约 94 GiB RAM。镜像容器默认 2 CPU / 2 GiB；源站 1 CPU / 768 MiB；独立浏览器客户端 2 GiB。4 CPU 对照仅调整镜像测试容器配额。
- Chrome 156，1280×900，DPR 1，无字体混淆池。每轮 UI 登录、进入项目、3 次预热创建、20 次正式创建；每次创建用独立 API 读取确认，最终检查 23 条唯一记录。全部场景通过。
- 主指标为 **按 Enter 到任务行在客户端 DOM 中可观测**：不包含此前键入耗时，镜像在按 Enter 前用 ping 屏障排空已接收输入；包含 Puppeteer/CDP 调用与 requestAnimationFrame 轮询等待。frame 指标也是镜像 DOM 状态，**不是 PNG 最终绘制到屏幕的时延**。
- 冷启动为打开页面到登录 DOM 就绪，镜像还需收到 sync-ready；仅一轮一次，未计算冷启动分位数。服务端 origin.goto 包含 networkidle0 等待，不等同于 CPU 执行时间。
- 资源每 500ms 采样，容器 memory.current 包含 Chromium、Node 和文件缓存；CPU 为整个测试生命周期的平均核数，包含启动/空闲/回收。WS 字节仅是消息 payload，包含登录、导航和预热，不含 HTTP 静态资源、TCP/TLS 开销，不能当单次提交流量。

## 基线观察

直连 2 轮，DOM/frame 各 3 轮；每轮 20 个正式样本。下表是各轮统计值的范围，不是合并后的分位数。

| 指标 | 直连 | DOM | frame |
|---|---:|---:|---:|
| Enter → 任务 DOM P50 | 27.3–28.2ms | 53.3–59.6ms | 58.4–65.8ms |
| Enter → 任务 DOM P95 | 30.9–32.5ms | 66.4–106.6ms | 117.7–147.9ms |
| 冷启动登录 DOM 就绪 | 274–284ms | 1241–1927ms | 1485–1646ms |
| 镜像容器采样峰值内存 | — | 309–403MiB | 492–513MiB |
| 镜像容器平均 CPU | — | 0.29–0.33 核 | 0.73–0.80 核 |
| 整轮 WS 下行 payload | 不适用 | 约 4.3MiB | 约 8.5–8.7MiB |

这些样本不支持 P99、最大并发、长时间稳定性或跨网络性能结论。不同轮次存在抖动，不能把某一轮 P95 当成稳定承诺。

在 dom-control/frame-control 中分段计时得到：

| 环节 | P50 | 样本数 | 含义 |
|---|---:|---:|---|
| DOM 快照克隆与清理 | 1.0ms | 6 | 页面内执行，不含 CSS 获取和 HTML 跨进程返回 |
| DOM 快照 CSS 收集/获取 | 7.4ms | 6 | 包含异步 fetch 等待 |
| DOM snapshot.evaluate | 14.2ms | 6 | 包含页面执行、等待和 CDP 传输，不能与其内部计时相加 |
| frame 整页截图 | 71.6ms | 5 | CDP captureScreenshot |
| frame PNG 解码 | 5.05ms | 192 | base64 转 Buffer + sharp raw RGBA |
| frame JS 扫描（有变化） | 1.28ms | 164 | 逐像素比较及脏行标记 |
| frame JS 扫描（无变化） | 1.29ms | 27 | 需要检查全部像素 |
| frame 每块裁剪与 PNG 编码 | 2.34ms | 218 | 每帧可能有多块，不等于每帧总编码耗时 |

三轮 frame 的“解码 + 扫描 + 裁剪编码”累计 wall time 中，扫描约占 12.4%–14.7%。这只是所测处理段的占比，不是整条请求链路或 CPU 占比；即使把扫描耗时完全消除，对这三段合计耗时的减少也只有该比例。

代码中还有明确的重复工作候选：每个全量快照重新获取 CSS；frame 先解码整帧扫描，再对每个矩形从原 PNG 重新建立裁剪编码管线；PNG 还经过 base64 和 JSON 包装。减少这些工作的实际收益尚需后续对照实验，当前未实施优化。

## Rust / Wasm 内核对照

直接提取 server.js 当前 JS 扫描函数，对照同语义 Rust 实现。输入来自实际捕获的 1280×900 RGBA 帧：11 对相邻帧、1 对完全相同帧，另加阈值 2、仅 alpha 变化、最后像素变化三个边界，共 15 对。

逐行校验 Wasm 与 JS 的完整脏行掩码，原生 Rust 检查变化行数；全部通过。两种运行目标都由同一 Rust 源码、Rust 1.99.1、edition 2024、`-O` 构建，无外部 crate。原生为静态 musl 可执行文件，Wasm 为 wasm32-unknown-unknown。独立无网络容器 2 CPU / 1 GiB，JS/Wasm 全局预热 1500 次；每个实现每对输入再预热 10 次、计时 50 次。

以下为 **15 对输入各自 P50 的中位数**，不是业务延迟或统一样本池的 P50：

| 实现 | 扫描及指定边界成本 |
|---|---:|
| 原 JS | 0.77ms |
| Rust 原生内核 | 0.29ms |
| Rust → Wasm，仅内核 | 0.33ms |
| Wasm，每次复制两帧并复制输出 | 1.02ms |
| Wasm，保留上一帧、只复制新帧及输出 | 0.56ms |

双帧复制为 9,216,000 bytes/次；保留上一帧后新帧复制为 4,608,000 bytes/次。后一种方式有小幅收益，但需要重做帧内存归属。原生数据不包含 Node 原生模块调用、进程启动或 IPC 成本；该内核尚未接入业务管线，因此不能声称业务性能已经提高。捕获帧只覆盖局部业务画面，不代表视频、全屏动画、高 DPR 等负载。

## 两项反事实实验

仅在内存中插桩的测试副本改变参数，生产默认行为保持原样。

| 模式 / 合并窗 | 任务 DOM P50 / P95 | dom-patches 消息数 | 整轮 WS payload |
|---|---:|---:|---:|
| DOM / 60ms | 53.3 / 104.8ms | 28 | 4.30MiB |
| DOM / 16ms | 65.3 / 72.8ms | 83 | 4.36MiB |
| frame / 60ms | 65.8 / 147.9ms | 37 | 8.66MiB |
| frame / 16ms | 65.4 / 83.2ms | 93 | 8.80MiB |

每条件只有一轮：尾延迟有所降低，但 DOM 中位数反而上升，消息数约增至 2.5–3 倍。数据说明合并/调度值得继续跟踪，**不能支持直接把默认窗口改成 16ms**。

frame 默认 2 CPU 的三轮基线存在约 1.8–4.6 秒累计 cgroup 节流计数。提高至 4 CPU 后两轮计数为 0/29ms，任务 DOM P95 为 105.6/115.5ms，仍存在明显尾延迟；平均 CPU 约 0.79–0.81 核。CPU 配额是影响因素，但既不能把平均 CPU 当峰值需求，也不能把尾延迟全部归因于配额或 JS。这不是 4 核容量建议。

## 复现入口与原始证据

当前源码已构建镜像时：

```bash
IMAGE=dom-mirror:local PROFILE=1 PROFILE_MODE=dom CASES=dom \
  BUSINESS_TEST_SCRIPT=profile-business.cjs EVIDENCE_DIR=artifacts/profile/dom \
  bash tools/verify-docker-vikunja.sh

IMAGE=dom-mirror:local PROFILE=1 PROFILE_MODE=frame CASES=frame \
  BUSINESS_TEST_SCRIPT=profile-business.cjs EVIDENCE_DIR=artifacts/profile/frame \
  bash tools/verify-docker-vikunja.sh
```

直连基线用 `CASES=direct`，省略 PROFILE；16ms 对照增加 `PROFILE_PATCH_MS=16`；4 CPU 对照增加 `MIRROR_CPUS=4`。每次使用不同 EVIDENCE_DIR。默认仍为原生产入口、2 CPU、60ms 合并窗。

Rust 内核可选，不是运行项目的依赖；需要对应 rustup targets。将二进制放入已捕获 frame PNG 的证据目录，再在同一 Node 镜像执行比较：

```bash
rustc --edition=2024 --target wasm32-unknown-unknown --crate-type cdylib -O \
  tools/fixtures/profile-scan.rs -o artifacts/profile/frame/scan.wasm
rustc --edition=2024 --target x86_64-unknown-linux-musl -O \
  tools/fixtures/profile-scan.rs -o artifacts/profile/frame/scan-native

docker run --rm --network none --memory 1g --cpus 2 \
  -v "$PWD/tools:/app/tools:ro" \
  -v "$PWD/artifacts/profile/frame:/evidence" -e PROFILE_DIR=/evidence \
  --entrypoint timeout dom-mirror:local 120 node tools/profile-scan.cjs
```

`node tools/profile-server.cjs --check` 校验插桩锚点和实际注入的页面脚本；源代码改变后锚点不匹配会失败。插桩会增加计时、采样和少量帧文件写入开销，应作为定位工具，不能代替低干扰正式基准。

本轮证据根目录：`/home/Kei/dom-mirror-validation/20261026/performance/`。各子目录的 profile-client.json、server-profile.json、应用/镜像版本和日志对应同一次运行；environment.json 保存主机/构建信息，frame-1/scan-comparison.json 为最终内核对照，scan-final.log 为对应执行日志。早期字段 enterToVisible 实际也是 DOM 存在性检查；后续已改名 enterToTaskDom，不应解读为 frame 像素呈现时间。

## 续测

[PNG 解码复用与客户端绘制续测](2026-10-26-codec-and-presentation.md)已完成：增加画布标记、绘制负对照和 ABBA 业务实验。多块回放收益明显，当前单会话创建任务的绘制延迟未稳定下降；不改变本报告的基线口径。

## 后续优先级

1. 增加源站事件、补丁入队/flush、客户端应用、frame 实际绘制的关联序号和时间点，定位尾延迟来源；不要拿 sstats.inLat 代替端到端指标。
2. 对 frame 做 PNG 解码复用和编码/传输工作量对照，记录 CPU、延迟、字节与图像正确性；DOM 则优先评估快照与 CSS 重复收集。
3. 仅当剩余扫描成本在目标负载下变成主要限制，再评估原生模块或保留帧内存的 Wasm；保持现有 JS 服务编排，不先重写。
4. 以上结论不能替代 1/3 会话负载、实际像素呈现、长稳、故障回收及跨网络验收。
